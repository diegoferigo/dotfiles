## Scratch files and heavy artifacts: keep them off `/tmp`

Check first whether `/tmp` is a tmpfs or otherwise RAM-backed mount. It often is on modern Linux. If it is, avoid writing scratch files there. Large scratch files are especially dangerous: build trees, package artifacts, datasets, model checkpoints, logs, extracted archives. They eat memory and can freeze the machine, and everything under `/tmp` is wiped on reboot, so a crash loses it all.

Put output on disk instead, under a scratch directory in the repo (add it to `.gitignore`) or elsewhere in `$HOME`, and clean it up when done.

## Verify before pushing

Before any commit is pushed:

1. Build the packages that were touched.
2. Run the targeted tests for them.
3. Run the linter.
4. Confirm the working tree is clean and you are on the intended branch.

Report the commands that were actually run and their outcome. If one of them was skipped, say which and why. A pre-commit run that reformats files returns non-zero: re-run it and confirm it is clean before claiming it passes.

## Stop and ask

See "Ask instead of guessing" in `~/.copilot/copilot-instructions.md`. It applies to every command in this file.

For a non-trivial or irreversible decision, get one adversarial second look before it stands: spawn a `rubber-duck` subagent, hand it the diff and the constraints (not your conclusion), and ask it to find what is wrong. Only when it earns the cost, never on a rename or a one-liner.

## Branches and stacks

- Branch names and older personal-repo patterns are in [identity.md](identity.md).
- For stacked pull requests use the `gh-stack` skill; do not improvise a manual rebase chain.
- When a branch you depend on was rebased (its commits kept their content but got new SHAs), do not merge the two histories. Replay only your own commits with `git rebase --onto <new-base-tip> <old-base-tip>`, so the duplicated base commits do not resurface as conflicts.
- Keep a generally useful fix out of a stack: land it standalone against the trunk, then drop the duplicate from the stack after it merges.
- He merges with a merge commit rather than squashing, unless the repo enforces otherwise. Do not squash someone's history on his behalf.
- Force-push is only for a branch that is still his own: a not-yet-reviewed branch, or a stack he owns where the layers above a new `Address review:` commit are restacked by plain rebase. The moment a PR on an upstream open-source repo is out for review, that door closes: stop amending and force-pushing, switch to follow-up commits, and let the maintainers squash on merge (see the guest rule in [collaborating.md](collaborating.md)).

## Repo conventions he sets up himself

Useful when creating a new repo or when asked what is missing from one. All of these are consistent across his recent projects.

- `src/` layout, `tests/`, `examples/`, and a `LICENSE`. BSD-3-Clause for research and robotics code, MIT for pure tooling. No GPL.
- No `CHANGELOG.md`. Release notes are generated by GitHub from PR titles, with bots excluded in `.github/release.yml`.
- Version numbers come from git tags through `hatch-vcs` or `setuptools_scm`, never hardcoded.
- `.pre-commit-config.yaml` with pre-commit.ci configured as `autofix_prs: false` and a quarterly autoupdate.
- `dependabot.yml` limited to GitHub Actions, monthly, grouped into one PR.
- `CODEOWNERS` kept accurate, including when maintainership is handed over.
- `CITATION.cff` and a BibTeX block in the README for research code.
- The README is the public face of the project. Keep it simple, clear, light, readable and concise, so a new user can follow it without excessive detail. Put deep details in dedicated docs, not in the README. If the repo has an `AGENTS.md`, its agent instructions extend the README, they do not repeat it.

## CI conventions

- One `ci_cd.yml` per repo triggered on `push`, `pull_request`, `release: published`, `workflow_dispatch` and a nightly `schedule`.
- `fail-fast: false` on every test matrix.
- Build the package once, then test the built artifact rather than the source tree.
- `fetch-depth: 0` on checkout wherever the version is derived from tags.
- Publish to PyPI with an OIDC trusted publisher and `skip-existing: true`, never with a stored token.
- Environments come from `conda-forge` only, driven by `pixi` with a committed lockfile, and a scheduled job that opens the lockfile-update PR.

## Shared working tree etiquette

Another agent or another session may be operating in the same checkout.

- Do not switch branches without explicit authorization from Diego.
- Do not stash, reset or clean work you did not create.
- If you find the tree on an unexpected branch, or you leave it on a different branch than you found it, say so explicitly in your report.
